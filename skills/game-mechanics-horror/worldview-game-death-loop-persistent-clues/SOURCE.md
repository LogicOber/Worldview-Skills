## Original design question

The method asks when repeated death becomes investigation rather than repeated labor.

The answer developed here is that a completed pass must produce an actionable fact, reset must follow a comprehensive state ledger, permitted knowledge or marks must persist, and the next pass must support a different decision whose consequence confirms or revises the player's model.

## Authored decisions

- treating loop reset as a locked transaction with explicit restoration order;
- classifying state as reset, persist, transform, external, or ephemeral;
- requiring every progression clue to connect to a later action and changed consequence;
- preferring demonstrated player knowledge over arbitrary hidden gates;
- separating restart-loop, resume-pass, leave-loop, new-profile, and delete-save operations;
- prohibiting fake corruption and preserving honest system UI;
- requiring fault-aware save verification and loop identifiers for delayed network work;
- testing one complete two-pass proof before expanding the narrative.

These are original design proposals, not claims that every loop game should use identical pacing or persistence.
